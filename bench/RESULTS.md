# 락 전략 비교 — 측정 결과

> **측정 조건을 먼저 밝힌다.** MacBook 로컬 Docker 의 MySQL 8 단일 인스턴스,
> 동시 요청 30, 총 600회, 풀 3,000개. 운영 환경이 아니다.
> **절대값은 의미가 없고 전략 간 상대 차이만 본다.**
> 같은 코드가 CPU 서버와 GPU 서버에서 크게 달랐다는 사례도 있는 만큼,
> "로컬에서 빨랐다"는 근거가 되지 않는다.

재현: `python -m bench.run --workers 30 --ops 600 --pool 3000`

## 결과

| 전략 | 정확 | 처리량/s | p50 | p95 | p99 | 최대 | 재시도 | 데드락 |
|---|---|---|---|---|---|---|---|---|
| `for_update` | OK | 246 | 83ms | 289ms | 442ms | 706ms | 0 | 0 |
| **`skip_locked`** | OK | **1488** | **19ms** | **27ms** | **31ms** | **31ms** | 0 | 0 |
| `conditional_update` | OK | 183 | 58ms | 316ms | **1727ms** | 2258ms | **6200** | 0 |
| `conditional_update_spread` | OK | 680 | 19ms | 164ms | 399ms | 590ms | 571 | **28** |
| `conditional_update_spread_tx` | OK | 728 | 29ms | 87ms | 123ms | 152ms | 428 | 0 |
| `redis_lock` | OK | 178 | 149ms | 392ms | 411ms | 417ms | 8680 | 0 |

**여섯 가지 모두 정확했다.** 중복 할당은 한 건도 없었다.
속도를 비교하기 전에 이걸 먼저 확인했고, 정확하지 않으면 나머지 숫자는 볼 필요가 없다.

## 읽은 것

### 1. `SELECT ... FOR UPDATE` 는 평균이 아니라 꼬리에서 무너진다

p50 은 83ms 인데 p99 는 442ms, 최대 706ms. **평균만 보면 안 보인다.**
모든 요청이 맨 앞의 같은 행을 잠그려 하므로 뒤에 온 요청은 앞 트랜잭션이
커밋할 때까지 줄을 선다. 대기 시간이 곧 응답 시간이 된다.

### 2. `SKIP LOCKED` 가 이 문제에는 압도적으로 맞다

처리량 6배, p99 는 14배 낮다. 그리고 **p50 과 p99 의 차이가 거의 없다**(19ms vs 31ms).
줄을 서지 않으니 꼬리가 생기지 않는다.

"아무거나 하나면 된다"는 할당 문제에서는 잠긴 행을 건너뛰는 게 문제의 모양과 정확히 맞는다.

### 3. 조건부 UPDATE 의 함정은 락이 아니라 "모두가 같은 행을 고른다"는 것

`conditional_update` 는 락을 쓰지 않는데도 p99 가 1,727ms 로 가장 나빴다.
**재시도가 6,200회.** 600번 성공하는 데 6,200번 실패했다.

원인은 락이 아니다. 모든 요청이 `ORDER BY id LIMIT 1` 로 **같은 첫 번째 행**을 집기 때문이다.
한 명이 이기면 나머지 29명이 전부 실패하고, 다시 같은 행을 집는다.

후보를 앞쪽 20개 중에서 무작위로 고르게 하자(`conditional_update_spread`)
재시도가 6,200 → 571 로, 처리량은 183 → 680 으로 바뀌었다.
**같은 방법인데 후보 선택만 바꾼 결과다.**

### 4. 그런데 후보를 분산했더니 데드락이 났다 (28건)

이게 이 측정에서 가장 많이 배운 부분이다.

`SHOW ENGINE INNODB STATUS` 를 확인했다.

```
TRANSACTION 19163, ... LOCK WAIT 7 lock struct(s), 11 row lock(s)
  UPDATE ... WHERE id = 404 AND status = 'AVAILABLE'
TRANSACTION 19124, ... LOCK WAIT 5 lock struct(s), 12 row lock(s)
  UPDATE ... WHERE id = 402 AND status = 'AVAILABLE'
*** WE ROLL BACK TRANSACTION (2)
```

한 행만 바꾸는 UPDATE 인데 **한 트랜잭션이 11~12개의 행 락을 쥐고 있었다.**

재시도 루프가 트랜잭션 **안**에 있었기 때문이다.
실패한 시도도 락을 잡고, 그 락이 트랜잭션이 끝날 때까지 풀리지 않고 쌓였다.
거기에 후보를 무작위로 고르니 트랜잭션마다 락을 잡는 순서가 달라졌고,
**순환 대기**가 만들어졌다. 데드락 네 조건 중 하나가 그대로 성립한 것이다.

반대로 `conditional_update` 는 데드락이 없었다. 모두가 같은 행을 같은 순서로 집으니
순환이 생길 수 없었다. **경합이 심한 쪽이 오히려 데드락은 없었다.**

### 5. 고친 방법: 재시도를 트랜잭션 밖으로

시도 하나를 트랜잭션 하나로 만들었다(`conditional_update_spread_tx`).
실패하면 즉시 커밋되어 락이 바로 풀린다.

| | 처리량 | p99 | 최대 | 데드락 |
|---|---|---|---|---|
| 재시도가 트랜잭션 **안** | 680 | 399ms | 590ms | **28** |
| 재시도가 트랜잭션 **밖** | 728 | **123ms** | **152ms** | **0** |

데드락만 사라진 게 아니라 **꼬리 지연이 3배 이상 좋아졌고 처리량도 올랐다.**
불필요하게 오래 쥐고 있던 락이 다른 요청을 막고 있었다는 뜻이다.

> 락과 트랜잭션의 **경계와 순서**가 방법 선택보다 결과에 더 크게 작용했다.
> 같은 조건부 UPDATE 인데 경계를 어디에 두느냐로 p99 가 1,727ms → 123ms 까지 움직였다.

### 6. Redis 락은 이 문제에 맞지 않았다

처리량 178, 재시도 8,680 으로 가장 나빴다.
후보를 고르는 방식이 `conditional_update` 와 같아 경합은 그대로인데,
락 획득/해제로 **네트워크 왕복이 두 번** 더 붙기 때문이다.

숫자를 떠나 더 중요한 건 **방어가 DB 밖에 있다**는 점이다.
Redis 가 흔들리면 방어도 함께 사라진다. 이 문제처럼 잠글 행이 이미 DB 에 있다면
DB 원자성을 먼저 검토하는 게 맞다고 본다.

Redis 락이 필요한 경우는 **잠글 대상이 아직 없을 때**다.
조회 후 없으면 생성하는 구조에서는 잠글 행 자체가 없어서 DB 로 막을 수 없다.

## 결론

| 상황 | 선택 |
|---|---|
| "아무거나 하나" 할당 (MySQL 8+) | **`SKIP LOCKED`** |
| MySQL 5.7 등 `SKIP LOCKED` 없음 | 조건부 UPDATE + **후보 분산** + **재시도는 트랜잭션 밖** |
| 특정 행 하나를 꼭 가져가야 함 | `FOR UPDATE`. 대신 꼬리 지연을 감수하거나 대기 한도를 둔다 |
| 잠글 행이 **아직 없음** | 분산락. DB 로는 막을 수 없다 |

그리고 어떤 방법을 쓰든 **마지막 방어선은 DB 제약**에 둔다.

## 이 측정의 한계

- 로컬 단일 MySQL. 네트워크 지연, 복제 지연, 커넥션 풀 포화가 빠져 있다.
- 풀이 3,000개로 넉넉하다. 자원이 거의 소진된 상태(경합 최대)는 따로 봐야 한다.
- `redis_lock` 은 같은 호스트의 Redis 라 네트워크 비용이 실제보다 작게 잡혔다.
