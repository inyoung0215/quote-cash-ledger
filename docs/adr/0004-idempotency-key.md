# ADR-0004. 견적 발송에 멱등 키를 필수로 받는다

## 맥락

`POST /v1/quotes` 는 호출할 때마다 보류가 생기는 **비멱등** 요청이다.
클라이언트는 타임아웃이 나면 결과를 모르는 채로 재시도한다.

**가장 위험한 건 실패가 아니라 됐는지 모르는 상태다.**
실패는 다시 하면 되지만, 모르는 상태에서 다시 하면 두 건이 된다.

## 결정

`Idempotency-Key` 헤더를 **필수**로 받는다. (선택이 아니라 필수)

- 같은 키 + 같은 내용 → 저장된 응답을 그대로 돌려준다 (`Idempotent-Replay: true`)
- 같은 키 + 다른 내용 → 422. 키를 재사용하고 있다는 뜻이므로 조용히 넘기면 안 된다
- 조회·기록·보류를 **하나의 트랜잭션**에 둔다. 조회만 먼저 커밋하면 그 사이에 끼어들 수 있다
- 동시에 같은 키가 들어와 PK 충돌이 나면 409로 물러난다. 다시 부르면 저장된 결과를 받는다

## 왜 헤더인가

본문에 넣으면 요청 내용의 일부가 되어, 같은 요청인지 판단하는 기준과 섞인다.
헤더로 분리하면 "이 요청이 무엇인가"와 "이 요청이 몇 번째 시도인가"가 나뉜다.

## 외부에 API를 여는 입장이 되어 보고 느낀 것

외부 기관 API를 호출하는 쪽을 오래 했는데, 멱등 키가 없는 API가 가장 곤란했다.
타임아웃이 나면 결과를 알 방법이 없어서, 중복을 피하려고 조회 API를 먼저 부르는
우회를 만들어야 했다. 그래서 이 레포에서는 필수로 뒀다.

같은 이유로 에러 응답에 `code` 를 함께 내려준다.
**비즈니스 거절을 5xx로 주면 중간 계층이 재시도해도 되는 것으로 오해하고,
그게 곧 중복 과금이 된다.**
