# ADR-0008. 시각은 전부 UTC 로 저장한다

## 결정

애플리케이션은 `app/clock.py` 의 `utcnow()` 만 쓴다.
`datetime.now()` 를 직접 부르지 않는다. 린트(DTZ005)로 강제한다.

MySQL `DATETIME` 은 타임존을 저장하지 않으므로, UTC 기준 값을 tz 없이 넣는다.
표현 시점의 타임존 변환은 API 경계 밖(클라이언트)의 일로 뒀다.

## 이유

`datetime.now()` 는 **서버의 로컬 시각**을 돌려준다.
서버가 여러 대이거나 컨테이너의 TZ 설정이 다르면, 같은 컬럼에 서로 다른 기준의
시각이 섞인다. 그리고 **한 번 섞이면 어느 행이 어느 기준인지 사후에 구분할 수 없다.**

이 도메인에서는 특히 위험하다. 48시간 만료가 시각 비교로만 판단되기 때문에,
9시간 어긋난 값이 섞이면 **아직 안 지난 보류가 해제되거나, 지난 보류가 안 풀린다.**
그리고 그 사이에 열람이 오면 확정과 해제 중 어느 쪽이 맞는지도 갈린다.
로그에는 아무 오류도 남지 않는다.

## 배경

숨고 기술 블로그의 MariaDB → MongoDB 이전 글에서, 옮기는 과정에 실제로 걸린 문제로
**시간대**(RDB 로컬 vs Mongo UTC)와 ID 체계 두 가지를 꼽았다.
저장소를 옮기는 작업이 아니어도 같은 문제가 생길 수 있다고 보고 처음부터 고정했다.

## 대가

- DB를 직접 조회하면 사람이 읽기에 9시간 어긋나 보인다. 운영자가 혼동할 수 있다.
- 그래서 *어디서* 변환하는지가 중요하다. 한 군데(표현 계층)에서만 바꾸고,
  중간 어디에서도 다시 바꾸지 않아야 한다. 두 번 변환하는 게 안 하는 것보다 나쁘다.
