# 실패 시나리오 목록

구현을 시작하기 전에 먼저 적은 목록이다.
정상 흐름만 보고 설계했다가 운영에서 문제를 겪은 적이 있어서, 이제는 이 문서를 먼저 쓴다.

각 항목은 `무슨 일이 일어나는가 → 누가 손해를 보는가 → 무엇으로 막는가` 순서다.

---

## 1. 열람과 만료가 경계 시각에 동시에 일어난다

48시간이 막 지난 순간에 고객이 견적을 연다.

- **둘 다 성공하면**: 고수는 과금당하고 환급도 받는다 → 회사 손해
- **둘 다 실패하면**: 보류가 영원히 남아 고수의 잔액이 묶인다 → 고수 손해

**막는 법**: 확정과 해제 모두 `status = 'HOLD'` 일 때만 바꾸는 조건부 UPDATE.
먼저 선점한 쪽만 영향 행 1을 받고, 나머지는 0으로 물러난다.
→ `tests/test_capture_expire_race.py`

## 2. 같은 열람 이벤트가 두 번 도착한다

이벤트 전달은 최소 한 번(at-least-once)이 전제다. 중복은 정상이다.

- **막지 못하면**: 한 번 열람에 두 번 과금 → 고수 손해, 문의 발생

**막는 법**: 1번과 같은 조건부 UPDATE. 두 번째부터는 영향 행 0이 되고,
이미 확정된 건이면 오류가 아니라 **같은 결과를 그대로 돌려준다**(멱등).
추가로 `UNIQUE(quote_id, entry_type)` 로 원장 중복을 DB가 막는다.
→ `tests/test_idempotent_view.py`

## 3. 고수가 견적을 동시에 여러 건 보내 잔액을 넘긴다

잔액을 읽고 판단한 뒤 쓰는 사이에 다른 요청이 끼어든다.

- **막지 못하면**: 사용 가능 잔액이 음수가 된다 → 회사 손해

**막는 법**: 보류를 늘리는 UPDATE 의 WHERE 절에 잔액 조건을 함께 넣는다.
분배 계산은 방금 읽은 값으로 하되, 반영은 조건부 UPDATE로 한다.
밀리면 다시 읽어 재분배한다(낙관적 재시도 3회).
→ `tests/test_concurrent_balance.py`

## 4. 클라이언트가 타임아웃 후 재시도한다

가장 위험한 건 실패가 아니라 **됐는지 모르는 상태**다.

- **막지 못하면**: 견적이 두 건 발송되고 보류도 두 건 잡힌다

**막는 법**: `Idempotency-Key` 헤더 필수. 같은 키면 저장된 응답을 그대로 돌려준다.
같은 키에 다른 내용이면 422로 거부한다.
마지막 방어선은 `UNIQUE(quote_id)`.
→ `tests/test_idempotency_key.py`

## 5. 만료 워커가 두 번 돌거나, 여러 대가 동시에 돈다

배포 중에는 구·신 버전 워커가 함께 떠 있을 수 있다.

**막는 법**: 해제 자체가 조건부 UPDATE라 두 워커가 같은 건을 집어도 한쪽만 성공한다.
그래서 워커에 분산락을 걸지 않았다 → ADR-0002
→ `test_release_is_safe_to_run_twice`

## 6. 만료 워커가 아예 돌지 않거나 늦는다

- **결과**: 보류가 오래 남아 고수 잔액이 묶인다. 돈이 잘못 빠지지는 않는다.

**판단**: 정합성 문제가 아니라 지연 문제로 분류했다.
조회 시점에 만료 여부를 함께 판단하면 정리가 늦어도 사용자에게는 정확히 보인다.
(현재 미구현 — 아래 '아직 안 한 것' 참고)

## 7. 금액 계산에 오차가 쌓인다

- **막지 못하면**: 건당으로는 안 보이다가 정산 합산에서 대사가 어긋난다

**막는 법**: 전 구간 `Decimal`, DB는 `NUMERIC(18,2)`.
입력은 반드시 문자열을 거쳐 `Decimal` 로 만든다 (`Decimal(0.1) != Decimal('0.1')`).
→ `tests/test_money_precision.py`

## 8. 고수가 "왜 이 금액이 빠졌냐"고 묻는다

기술 실패는 아니지만 설계로 답해야 하는 요구다.

**막는 법**: 원장을 덮어쓰지 않는다. 보류·확정·해제를 각각 남기고,
어느 재원(유상/보너스)에서 얼마가 움직였는지도 함께 기록한다 → ADR-0003

## 아직 안 한 것 (의도적으로 남긴 것)

레포를 작게 유지하려고 뺐다. 실제 서비스라면 필요하다.

- **조회 시점 만료 판단** — 6번의 완전한 해결. 지금은 워커에만 의존한다.
- **원장 대사 배치** — 지금은 테스트가 `assert_ledger_matches_account` 로 부르지만,
  운영이라면 주기적으로 돌면서 어긋난 계정을 알려야 한다.
- **멱등 레코드 만료** — 무한히 쌓인다. TTL이나 정리 배치가 필요하다.
- **Alembic 마이그레이션** — ADR-0007
- **인증·인가** — 전부 열려 있다. 학습용 범위 밖으로 뒀다.
