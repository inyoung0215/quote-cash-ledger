# AI 사용 기록

이 레포는 **코딩 에이전트(Claude Code)와 함께** 만들었다.
숨고 백엔드 팀이 AI를 기본 환경으로 쓰면서도 "검증 루프 없이 올리지 않는 사람"을 찾는다고 해서,
결과물뿐 아니라 **어떻게 맡기고 어떻게 검증했는지**를 남긴다.

## 기준: 틀렸을 때 내가 알아챌 수 있는가

| | 맡긴 것 | 이유 |
|---|---|---|
| ✅ | 보일러플레이트 (SQLAlchemy 모델, Pydantic 스키마, FastAPI 라우터 배선) | 틀리면 즉시 드러난다. 임포트가 깨지거나 스키마가 안 맞는다 |
| ✅ | 테스트 케이스 초안 | 내가 빠뜨리는 경계 조건을 끌어내는 데 효과가 크다 |
| ✅ | 환경 설정 (docker-compose, pyproject, Makefile) | 돌려보면 바로 안다 |
| ✅ | Python 관용구 확인 (`Decimal` 생성, async 세션 관리) | 언어 전환 중이라 숙어를 빠르게 익히는 용도 |
| ❌ | **상태 전이 설계** (HOLD → CAPTURED / RELEASED) | 틀려도 테스트가 통과할 수 있고 운영에서야 드러난다 |
| ❌ | **조건부 UPDATE의 WHERE 절에 무엇을 넣을지** | 이 한 줄이 정합성의 전부다 |
| ❌ | **재원 분배 정책** (보너스 우선) | 기술 판단이 아니라 고수 손익에 직결되는 정책 |
| ❌ | **트랜잭션 경계** | 어디서 커밋하느냐가 곧 실패했을 때 남는 상태다 |

직접 판단한 것들은 `docs/adr/` 에 왜 그렇게 정했는지 남겼다.
AI에게는 결론 대신 **내 설계의 반대 논거**를 요청하는 방식으로 썼다.

## 검증 루프

1. **범위와 완료 조건을 먼저 정하고** 한 번에 한 단위씩 맡긴다.
   이 레포에서는 `docs/failures.md`(실패 시나리오 목록)를 코드보다 먼저 확정했다.
   막을 대상이 정해져야 "다 됐다"를 판단할 수 있다.
2. **diff 를 직접 읽는다.** 특히 `app/services/cash.py` 의 `WHERE` 절.
3. **생성된 테스트는 믿지 않는다.** 구현을 일부러 깨뜨려 실제로 실패하는지 확인한다.
   → 결과 전부: [`docs/verification-log.md`](verification-log.md)

## 3번에서 실제로 걸린 것

경쟁 조건 테스트를 15라운드 돌리도록 만들어져 있었고 잘 통과했다.
그런데 `capture()` 의 상태 조건을 지우는 변이를 넣었더니 **15라운드가 전부 그대로 통과했다.**

`asyncio.gather` 가 넘긴 순서대로 태스크를 깨우기 때문에 늘 같은 쪽이 먼저 이겼고,
"해제가 먼저 이기는 순서"는 한 번도 재현되지 않고 있었다.
15번 돌린 게 아니라 같은 시나리오를 15번 반복한 것이었다.

라운드마다 순서를 뒤집도록 고친 뒤 같은 변이를 다시 넣으니 홀수 라운드 7개가 정확히 실패했다.

> **반복 횟수를 늘리는 것과 경우의 수를 늘리는 것은 다르다.**
> 통과하는 테스트를 보고 넘어갔으면 이 레포는 아무것도 증명하지 못했을 것이다.

## AI가 잘 못한 것

- **도메인 고유 제약이 개입하면 정확도가 떨어진다.** 보류/확정/해제에서 유상·보너스 재원을
  끝까지 분리해야 한다는 건 요구사항으로 명시하기 전까지 반영되지 않았다.
  단일 잔액 컬럼으로 만들면 미열람 환급 때 어느 재원으로 돌려줄지 정보가 사라진다.
- **트랜잭션 경계는 두 번 고쳤다.** 초안은 멱등 키 조회와 보류를 서로 다른 트랜잭션에 뒀다.
  조회만 먼저 커밋되면 그 사이에 다른 요청이 끼어들 수 있다.
